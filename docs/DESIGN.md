# 设计取舍

本文件记录「为什么是外部清理器」，以及被否决方案的理由。结论来自一次多模型会诊（7 个模型首轮 + 4 个红队复核），
并在真实实例上做了实测验证。

## 问题

实例是**第三方预编译镜像**部署（Docker Compose，服务器上没有源码、没有 `.git`，容器内只有编译后的 JS）。
上游 Misskey 从 2025.8.0 起有「旧远程帖清理」，而该镜像的基线（Sharkey 2025.5.2-dev 系）没有同步，
且镜像管线本身也长期停更。

同时在「改动最小」「对现有安装破坏最小」「未来仍能跟随上游更新」三条约束下选型。

## 候选方案与裁决

| 方案 | 裁决 | 理由 |
|---|---|---|
| **外部清理器**（本实现） | ✅ **采用** | 不改镜像/源码/schema；进程隔离，可随时停；上游发新镜像照常换、上游自带该功能后停 timer 即退役，零残留 |
| 薄派生镜像（`FROM` 现镜像 + `COPY` 覆盖编译产物，补 3 处注册点） | ⚠️ 次选 | 能让清理出现在应用自身的任务队列/日志里，但每次镜像升级都要重打补丁，且编译产物结构变化会**静默失效**；没有版本锚点 |
| bind mount 覆盖运行中镜像的编译产物 | ❌ | 比薄派生镜像更缺版本锚点，升级即漂移 |
| fork + 补丁 commit + 自建 CI 重建整个镜像 | ❌ | 只有当**源码基线可复现**时才可行。实测：镜像内版本串在公开仓库查不到、Docker Hub 的 `sha-` tag 提交在仓库 404、仓库当前 Dockerfile 已用 node 24 而线上跑 node 22 → 重建等于把线上应用换成一个更新版本（要跑新迁移、承担行为差异），破坏性大于功能本身。仅适合「把补丁提回上游」 |
| 纯 SQL 脚本（宿主 cron + `psql`） | ❌（被并入） | 需要自己处理游标/超时/退避/日志/结果形状，本实现的 SQL 语义与之等价但更省事 |
| 等上游同步 / 提 PR | 并行 | 无时间表，不能作为阻塞依赖 |

## 清理语义的来源

参考上游实现的行为定义（不复制代码）：

- **#16292**（Misskey 2025.8.0）：每日 04:00 系统任务，按 id 游标批量删除「早于保留期的远程帖」，排除被收藏/置顶/被本地回复的；
- **#16368**：改为递归 CTE 处理 renote/reply 树（整棵树都可删才删），修游标推进；
- **#16412**：保留有本地用户反应的帖；
- 现状：游标持久化、自适应批大小、处理 `statement_timeout`(57014) 与完整性错误(23xxx)。

本实现采用**等价但更保守**的规则：**只删叶子帖**（无任何子节点）+ 无置顶/收藏/clip/本地反应/本地回复。
叶子规则天然规避了自引用 `CASCADE` 误删本地内容的风险；代价是父帖要等子帖先被删、下一轮才轮到（实测只有
~3,948 条父帖因「子帖仍在保留期窗口内」被挡），以及被置顶/成环的帖永久残留 —— 量级可接受。

## 实测验证（2026-10-14，`note` 表 310 万行 / 3.79GB）

| 环节 | 结果 |
|---|---|
| dry-run 预演 | 90 天为界：候选 2,612,177；叶子可删 **1,761,997**；置顶保护 50,701；有子节点 801,512；子帖在窗口内被挡 3,948；估算可回收 ≈2.0GB |
| 小批试点 | 精确删除 500 行，`n_tup_del` 增量 +500，应用容器健康、日志无新增异常类型 |
| 吞吐诊断 | 初测 **140ms/行**（过慢）→ 定位为 `latest_note.note_id`(13ms) + `note_edit.replyId`(72ms) + `note_edit.renoteId`(55ms) 三个外键子表**缺索引**导致全表扫描；`CREATE INDEX CONCURRENTLY` 补上后 **7.4ms/行（19 倍）** |
| 实测吞吐 | `BATCH=2000` / `SLEEP_MS=500` → ≈130 行/秒 |
| WAL 风险 | `archive_mode=off`、复制槽 0、`max_wal_size=1GB` → WAL 由 checkpoint 回收，不会按行数撑满磁盘 |
| 应用侧噪声 | 日志中的 error 均为既有的中继签名失败（nya.one / moew.science），与本操作无关 |

## 已知的、被有意接受的风险

- 直删绕过应用层：父帖计数、`user.notesCount`、`hashtag` 计数、Redis 缓存不会回减/失效（`note` 表无触发器，计数由应用维护）。上游实现同样绕过应用。
- 删除不可逆；工具不负责备份（建议批量清理前自行 `pg_dump -Fc`）。
- 与应用并发时会偶发完整性竞态（`23xxx`），实现里按「记一次 transient error 并继续」处理。

## 红队复核中被采纳/驳回的要点

采纳：拆开 `NOT EXISTS(... OR ...)`、同时查 `clip_note`、单轮内存游标、单语句原子 DELETE 防 TOCTOU、
`VACUUM` 会话必须 `statement_timeout=0`、id 方法必须按实例配置识别、不用 `session_replication_role=replica` 图快。

驳回（实测反驳）：`docker run <镜像> node x.mjs` 会被 ENTRYPOINT 吞掉（实测 tini 会 exec 传入命令）、
`VACUUM FULL` 需要 2 倍表空间（实际是「表+索引」量级）、生成边界需要防时区/闰秒（对毫秒时间戳无意义）、
pgroonga 有 `disable_index_update` 扩展参数（不存在）。
